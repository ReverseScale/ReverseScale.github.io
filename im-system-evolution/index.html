从能聊到可靠：
一套 IM 系统的演进路线

IM 的难点从来不是把一句话从 A 发给 B，而是当网络抖动、进程退出、设备切换、服务扩容时， 这句话仍然只出现一次、顺序正确、状态可解释，并最终抵达该抵达的人。

问题定义

一个简单 IM 可以只有一条长连接和一个消息转发器；一个可信 IM 却需要同时回答四个问题： 消息是什么、是否送达、连接是否可用、状态如何恢复。 后续所有复杂度，本质上都从这四个问题展开。

网络层的“可靠传输”不等于业务层的“可靠消息”。TCP 可以把字节送到进程， 但无法保证进程已落库、用户已看见，或下一台设备知道这条消息存在。

01 · Evolution

先建立演进地图

不要一开始就把所有能力塞进系统。每一阶段只解决上一阶段暴露出的真实问题。

v1.0

能收发

接入用户、发送文本、维护会话列表。核心是建立连接、定义消息帧并完成转发。

Socket · Protobuf · local DB
v2.0

可恢复

补齐 ACK、序列号、心跳、重连、离线拉取，让消息在弱网和进程切换后可恢复。

ACK · Seq ID · heartbeat
v3.0

可扩展

拆分登录、消息、路由、存储与推送服务，支撑群聊、多端同步、检索和媒体消息。

routing · queue · sharding
v4.0

可替换

把传输、加密、协议和业务封装成稳定边界，让客户端能力可插拔、可跨平台。

TCP · TLS · WebSocket · C ABI

02 · Protocol

协议不是格式，而是边界

一个消息帧应让接收方在读取正文之前，就能判断长度、版本、用途与顺序。

length4 bytes version2 service2 command2 seq2 flags4
Protobuf bodyvariable length
fixed header / 16 bytes + typed payload

先解决字节边界

TCP 是字节流，没有“消息包”概念。一次发送可能被拆成多次读取，多次发送也可能在一次读取中合并。 因此接收端必须持续缓冲，并依据固定头部中的 length 字段切出完整帧。

再解决语义边界

service_id 决定消息属于登录、聊天还是群组服务，command_id 决定正文如何反序列化，seq_num 把请求、响应和重试关联起来。 

typedef struct {
  uint32_t length;      // header + body
  uint16_t version;     // protocol evolution
  uint16_t flags;       // compression / encryption
  uint16_t service_id;  // service boundary
  uint16_t command_id;  // message semantics
  uint16_t seq_num;     // request correlation
  uint16_t reserved;
} PduHeader;
选型原则

原生 TCP 提供最大控制力；WebSocket 更容易穿过代理并复用 Web 基础设施；MQTT 适合主题订阅与设备场景。 选择哪个传输层，不应改变上层的消息身份、确认与同步语义。

03 · Reliability

送达不是一个布尔值

“已发送”至少包含本地接受、服务端提交、接收端同步三个不同事实。

客户端Local ID

先落本地库，状态记为 pending；UI 不等待网络才出现。

→
接入层Request ID

同一次重试沿用同一幂等键，避免重复写入。

→
消息层Message ID

持久化成功后生成全局身份，再返回 server ACK。

→
接收端Sequence

按会话序列消费；发现空洞就触发补拉。

ACK 证明哪一步完成？

ACK 必须绑定明确语义。网络写入成功只证明字节进入套接字缓冲区；服务端 ACK 应在消息进入可靠存储后返回； 若产品需要“已送达”或“已读”，则由接收端分别产生新的回执事件。

重试为什么会制造重复？

客户端超时并不代表服务端失败。原请求可能已经落库，只是 ACK 丢了。 重试必须携带稳定的客户端消息 ID，服务端以此执行幂等写入，接收端再按服务端消息 ID 去重。

可靠消息公式 持久化 + 明确 ACK + 幂等重试 + 序列补洞

缺少任何一项，都只能得到“通常能到”的系统，而不是“故障后可解释”的系统。

04 · Connection

连接治理：检测、退避与恢复

心跳不是为了制造流量，而是为了缩短“连接已经失效但双方尚未察觉”的时间。

01

心跳自适应

前台与后台、Wi-Fi 与蜂窝网络使用不同间隔；服务端基于最后活跃时间回收幽灵连接。

02

重连带抖动

指数退避叠加随机抖动，避免服务恢复时所有客户端同时发起连接形成惊群。

03

恢复靠游标

连接成功不等于状态恢复。鉴权后提交最后消费序列，由服务端补发缺失消息。

网络切换是新连接。 IP、路由和 NAT 映射都可能变化。与其试图证明旧连接仍然有效， 不如快速废弃它，建立新连接，再用业务游标恢复状态。

05 · Client state

客户端不是服务端的投影

客户端需要一套可离线工作的本地事实，再通过同步协议逐步与服务端收敛。

conversation conversation_id last_message_id read_sequence unread_count
message local_id / server_id conversation_id sequence delivery_state
sync_cursor scope last_sequence updated_at schema_version

消息表负责不可变事实，发送状态允许单向推进；会话表保存摘要和已读位置；同步游标记录“本端确认消费到哪里”。 昵称、头像等易变信息不应复制进每条消息，而应通过用户资料缓存和变更事件更新。

06 · Services

服务端围绕消息路径拆分

拆分的目的不是画出更多方框，而是隔离不同伸缩模式、故障边界与数据职责。

在线路由与消息存储分开

在线状态短暂且高频，适合内存或 Redis；消息记录要求持久、可按会话顺序读取。 两者分离后，路由节点重启不会改变消息事实，存储扩容也不必迁移连接。

群聊先选择扩散模型

小群可写扩散，为每个成员维护收件序列；超大群更适合读扩散，保存一份群消息并由成员游标读取。 这不是永久二选一，系统可以按群规模与活跃度切换策略。

媒体与实时通话

图片、语音和视频正文应进入对象存储，IM 只传资源身份、校验信息和展示元数据。 音视频通话的信令可以复用 IM，媒体流则交给 WebRTC 或专用实时媒体基础设施；两条链路的可靠性目标不同。

07 · Operations

可用性必须能被观察

连接数和 CPU 只是资源信号；真正的业务健康度来自消息路径上的阶段指标。

连接在线连接数

建立成功率 · 鉴权延迟 · 重连率 · 心跳超时

消息端到端延迟

写入耗时 · ACK 延迟 · 重试率 · 重复率 · 序列空洞

同步游标落后量

离线补拉量 · 多端收敛时间 · 未读数修正次数

存储持久化成功率

分片热点 · 队列积压 · 索引延迟 · 备份恢复

99.9% 可用性 ≈ 每年 8.76 小时不可用

预算应分配给可感知的用户路径。连接可建立但消息持续积压，不能算作服务可用； 单个节点存活，也不能替代端到端探针和真实消息回环。

运维策略应覆盖分层隔离、水平分片、冗余、自动故障转移和容量保护。发布协议变更时，先保证旧客户端仍能解析新头部， 再灰度服务端，最后观察错误码、未知命令和反序列化失败是否异常上升。

08 · Principles

最后留下八条原则

  1. 01

    先定义消息身份，再讨论发送。 没有稳定 ID，就无法可靠重试和去重。

  2. 02

    ACK 必须绑定持久化事实。 “写入 socket”不是业务成功。

  3. 03

    顺序依赖序列，不依赖时间。 客户端时钟不可信，跨节点时间也不天然有序。

  4. 04

    重连之后一定要同步。 连接状态和业务状态是两条独立的恢复链。

  5. 05

    本地数据库是离线事实层。 UI 从本地状态工作，再与服务端逐步收敛。

  6. 06

    传输协议保持可替换。 TCP、WebSocket 或 MQTT 不应泄漏进消息语义。

  7. 07

    按数据职责拆服务。 连接、路由、消息、关系和索引有不同的生命周期。

  8. 08

    用端到端证据定义可用。 最终要证明一条消息能被提交、同步和恢复。

IM 的演进不是不断增加消息类型，而是不断收紧不确定性：把字节变成帧，把帧变成消息， 把发送变成可确认的提交，再把一次连接扩展成可以跨故障恢复的长期状态。
