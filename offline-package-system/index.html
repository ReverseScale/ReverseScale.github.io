Research note · Web delivery

不只是缓存：
一套移动端离线包系统如何发布、校验、回滚与观测

离线包真正解决的不是“断网还能打开页面”，而是如何把一组 Web 资源作为可追踪的发布制品， 安全地送进 App、切换为当前版本，并在任何一步失败时回到已知可用状态。

01 · Problem

先把离线包和 HTTP 缓存分开

两者都能减少网络请求，但它们管理的是不同层次的事实。

HTTP 缓存保存响应，并依据新鲜度、验证器和缓存指令决定何时复用；离线包则把一组相互兼容的 HTML、JavaScript、CSS 和图片固定为一个版本化发布单元。前者优化请求，后者控制客户端实际运行哪一套资源。

HTTP cache

逐响应复用

资源可能来自不同发布时间，由协议缓存语义决定命中、过期和再验证。

freshness · validator · revalidation
Offline package

整包一致切换

版本清单声明完整资源集合，客户端校验通过后一次性切换当前版本。

manifest · artifact · atomic activation
如果首页已经更新、业务脚本仍是旧版，缓存命中率再高也不是成功。离线包系统首先保障的是版本一致性，其次才是速度和离线可用。

02 · Topology

把控制面和客户端数据面拆开

控制面决定“应该运行什么”，客户端数据面负责“如何可信地运行它”。

制品应不可变

同一个版本号或内容地址必须永远指向相同字节。发布错误用新版本修正，不能偷偷替换 CDN 上的旧包。

清单表达期望状态

清单描述版本、入口、大小、摘要、签名、兼容范围与灰度策略；客户端把它与本地状态比较，而不是猜测目录内容。

03 · Manifest

版本清单是发布契约

它既是下载索引，也是完整性证明、兼容性边界和回滚依据。

Identitypackage + version

定位发布单元，支持幂等下载和事件关联。

Integritybytes + sha256

先验证长度，再验证内容摘要，避免截断或被替换。

CompatibilityminimumAppBuild

阻止新 Web 能力落到不支持的原生容器。

Authenticitysignature + key ID

确认清单来自受信发布者，而不只是在传输中没有损坏。

增量包是优化，不是正确性基础。 客户端应始终能退回完整包路径；差分合成后仍需按目标版本摘要重新校验。

04 · Delivery

交付是一条有提交点的事务

下载完成不等于发布成功。真正的提交发生在活动版本指针被原子切换时。

01Discover

拉取清单，比较当前版本、App 构建号和灰度规则。

02Download

写入 staging 目录；支持超时、断点和空间预算。

03Verify

校验清单签名、制品大小、摘要和解包约束。

04Prepare

解包后确认入口和必需文件，执行轻量预检。

05Activate

原子更新 current 指针，保留 last-known-good。

staging/42.7.1可删除的中间状态
verify ✓
packages/42.7.1不可变的已验证版本
atomic switch
current → 42.7.1唯一提交点

清理策略同样属于生命周期：先保护 current 与 last-known-good，再按最近使用时间和空间水位淘汰其余版本。绝不能让清理线程删除正在被 WebView 读取的目录。

05 · Interception

请求拦截必须保持 Web 语义

命中本地文件只是第一步；URL、来源、MIME、状态码和响应头仍要让 WebView 看见一致的世界。

iOS / WebKit

显式注册资源方案

WKURLSchemeHandler 可为 WebKit 原本不处理的 URL scheme 提供资源加载。实现必须正确响应任务开始、取消、MIME 与错误。

Android / WebView

优先保持 HTTPS 风格来源

WebViewAssetLoader 可通过 shouldInterceptRequest 将本地资源映射为 HTTP(S) URL，更容易维持同源策略和现代 Web 兼容性。

平台能力不是共享抽象

iOS 和 Android 的拦截入口不同，但上层契约可以一致：规范化 URL → 选择活动包 → 校验安全路径 → 返回带正确元数据的响应 → 记录命中结果。

06 · Recovery

失败降级不是“再试一次”

失败可能发生在清单、下载、校验、解包、激活或运行期；每个阶段都要保留下一条确定路径。

01 · preferredCurrent package

已校验且通过运行期健康检查的活动版本。

02 · recoveryLast-known-good

上一个成功运行版本；切换无需重新下载。

03 · baselineNetwork or bundled shell

远端页面可用时走网络，否则回到随 App 发布的最小壳。

失败阶段状态处理用户路径
清单不可达不改变 current继续使用本地已激活版本
下载或摘要失败删除 staging当前版本不受影响，退避后重试
激活后启动失败标记 bad version原子回滚 last-known-good
本地资源缺失记录 package miss按策略走网络或基线页

防止回滚风暴。 坏版本应进入设备侧抑制列表，并由服务端停止灰度；否则每次启动都会下载、失败、回滚，持续消耗流量和启动时间。

07 · Security

把离线包当成待执行代码

压缩包最终会向 WebView 提供 HTML 和 JavaScript，因此其信任要求不应低于原生更新或远程配置。

01

认证发布者

在 App 内置受信公钥或可轮换的密钥集合，验证清单签名；不能把服务端下发的新公钥自动当作可信根。

02

验证每个字节

签名覆盖版本、摘要、大小和兼容范围；制品下载后再按摘要验证，任何不匹配都不得激活。

03

约束解包边界

拒绝绝对路径、.. 穿越、符号链接逃逸、重复文件和超出大小或数量预算的条目。

04

隔离服务路径

只允许读取活动包根目录内的规范化路径；不把任意 file://、用户目录或 staging 暴露给 Web 内容。

关键告警应比较版本之间的差异：新版本的校验失败、首屏错误、本地 miss 或回滚率是否显著高于上一版本。没有版本维度，异常只会被全局平均值稀释。

09 · Boundaries

什么时候值得做，什么时候不值得

离线包提高发布控制力，也把一部分发布基础设施搬进了每台设备。

适合

高频 Web 业务

首屏时延敏感、弱网使用明显、资源集合可版本化，并且团队有能力维护灰度、回滚和监控。

适合

原生壳 + Web 模块

原生容器稳定，业务模块需要独立发布节奏，同时希望保留一致的安全与兼容性边界。

谨慎

内容型页面

若主要内容天然需要实时联网、更新频率低，标准 HTTP 缓存与 Service Worker 可能已经足够。

谨慎

缺乏发布治理

没有签名、灰度、回滚、事件模型和空间预算时，离线包会把网络问题变成更难清理的设备状态问题。

  1. 01

    以不可变制品为基础。 相同身份永远对应相同字节。

  2. 02

    清单定义完整发布契约。 版本、摘要、兼容与签名必须一起演进。

  3. 03

    下载和激活分离。 只有验证完成后的原子切换才算发布成功。

  4. 04

    始终保留已知可用版本。 回滚路径要比新版本路径更短、更确定。

  5. 05

    拦截器维护 Web 语义。 本地命中不能破坏来源、安全策略和响应元数据。

  6. 06

    用运行期证据完成发布。 激活不是终点，健康会话才是。
